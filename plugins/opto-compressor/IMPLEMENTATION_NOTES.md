# Craft Opto Compressor: implementation notes

Built only from `spec/opto-compressor/r1/SPEC.md` and its tables. Product code `COcp`, CLAP id
`com.craftaudio.opto-compressor`. Zero latency. VST3, CLAP, Standalone.

## Architecture
- `source/dsp/OptoEngine.h`: host-independent engine, per-sample, in double precision.
- `source/dsp/OptoTables.h`, `tests/SpecTables.h`: generated by `tools/gen_tables.py` from the spec tables and
  `tools/fit_dynamics.json` / `tools/fit_filters.json`. Do not edit.
- `tools/fit_filters.py`, `tools/fit_dynamics.py` + `fit_dynamics_sim.c`: offline fits (numpy, scipy), spec tables only.
  The dynamics script expects `sim.so` built from the C file next to it.
- `source/plugin`, `source/ui`: processor and original vector editor. `tools/Snapshot.cpp` renders the editor to PNG.

## Signal path and detector (spec section)
- Path (3): gain cell, colouration, Gain, Analog noise/hum, Mix with dry, Trim. No clipping.
- Level (4, 5): weighting filter, then a 16-pole quadrature all-pass pair; `sqrt(a^2+b^2)` reads the sine peak at any
  frequency with no look-ahead. Stereo uses the louder channel. The static table gives the total reduction G.
- Ballistics (7): fast state F plus slow memory state S, reduction = F + S. This differs from the spec's informative
  "deeper of the two" model; D1 lets the tables override it. Static G splits as `F + S_inf(F)`, so a steady tone ends
  exactly on the table.
- Waveform following (6): a zero-mean term at twice and four times the signal phase is integrated into the gain, scaled
  by the release rate. This gives H3 and H5 falling about 1/f under reduction.
- Colouration (6): fitted bells and a matched HF section for the response; weighted `x|x|` and `x^2` terms for the
  low-level harmonics, driven by the level after the gain cell.
- Analog (8): noise and hum are added in the wet path, so Mix 0 stays exactly dry.

## Tests
`tests/OptoTests.cpp` (Catch2, CTest prefix `opto-compressor/`) uses the spec tolerances at 44.1, 48 and 96 kHz. The attack,
release and t63/t90 cases each take about 150 s under CTest, because each process re-renders the bursts.

Test aids that shorten settling, which is worth knowing when reading the results:
- `primeSteady`: the 1 kHz static check at every table level divisible by 6 starts on the steady state rather than
  from rest. Five further points run from rest for 20 s. Other table levels are not tested directly.
- `settleMemory`: the Hi Freq check fills S directly after 0.6 s. Only levels divisible by 6 are checked.
- Harmonics are checked only where the table is above -90 dBc and the harmonic is below 0.45 fs.
- Release times are read from the 4 ms short-time gain on a 2 ms grid, limited to 15 s.

## Host stress
`craft_hoststress --editor` on the Windows Release VST3:
- 150 s, seed 1, stock limit (+40 dBFS): 674 flags. The 20 printed were all finite, 100 to 252 linear, consistent with
  Gain 10 + Trim +18 = +47.6 dB plus the HF rise on full-scale signals. The tool prints only the first 20.
- 150 s, seed 2, limit raised to 400 (+52 dBFS) in the build mirror only, not committed: 0 failures. The tool also fails on
  non-finite output, so that run had no NaN/Inf and nothing above +52 dBFS. The two runs used different seeds.
- All prepares logged in both runs were "in 2 ch", so the mono layout was not exercised by this host. The engine's mono
  path has a unit test; the mono bus layout in a real host has not been run.

## Deviations and limits
- The informative W values are not reproduced. Table `hifreq_gain.csv` shows the weighting narrowing with level, so the
  fit adds a level-dependent term (`bandDrop`), giving for example W(100 Hz) about -0.2 dB at low level rather than -0.85 dB.
  The table takes precedence (D1). For broadband program this term is an extrapolation, since the tables hold only sines.
- Fitted ripple terms were adjusted by hand against `harmonics.csv`; several harmonics sit near the edge of the ±6 dB
  tolerance. Likewise several Hi Freq points are close to ±0.5 dB.
- Linux: only the DSP tests were built and run (GCC). The plug-in targets were built on Windows only.
- Not listened to or run in a DAW. The Auto Makeup editor gesture is covered only for its rule, not by a UI test.
- The dynamic model is validated only on the 1 kHz bursts of the spec. Program material is untested (spec 12).

## Questions/assumptions
1. Short-time gain: 4 ms window centred on t, energy ratio of output to input. The spec does not state the alignment;
   centred fits the table's initial slope best.
2. t63/t90 are measured from the +5 ms value (`gr_end`).
3. Hum levels are sine peak dBFS; the same hum on both channels.
4. Noise is white and uniformly distributed; the spec gives only rms. Noise and hum are in the wet path, so they scale with Mix.
5. Noise at Gain 10 is modelled as a small pre-Gain part added to the post-Gain noise, from the +5 dB in `noise.csv`.
6. Levels above 0 dBFS continue with the last 4 dB slope of the static table.
7. Mono (D4): the same engine on one channel. Rates above 96 kHz use the same design and are untested.
8. Comp/Limit is a two-state choice parameter; a mode change crossfades the static curves within 20 ms.
9. Auto Makeup: user gestures (drag, wheel, double-click) are detected on the knob. Gain clamps at 0 and 10.
10. A non-finite input sample is treated as silence.
